2026-09-12，只读审计；未启动 GPU、SC2 或 PPO，未修改运行模块。

**结论：这四步没有直接训练“收到人口已满/失败反馈后，把 Depot 提到前面”。
后两步也没有从游戏回报中得到相对优劣信号。尚未发现新的实现 bug；不能据此

## 三项核对

| 问题 | 实际证据 | 能说明什么 |

| 是否遇到目标输入 | 108 条真实决策，人口余量最小 3；余量 0 为 0/108，失败反馈 0/108 | 未覆盖后来 05:49 那类明确人口阻塞/失败反馈输入；不等于执行队列中从未发生人口阻塞 |
| 是否采样了相反顺序 | 94 条合法回答中，Depot 先于 Marine/SCV 40 条，反向 45 条，不可比较 9 条；同一完整输入下合法的相反顺序对照为 0 组 | 两种顺序都出现过，但处于不同输入，不能解释为学到了“何时换顺序” |
| 是否有区分回报 | step3/4 各 16 答、每局两答、均合法、同批回报相等；日志 advantage/PG loss 都为 0 | 后两批没有可区分优劣的回报信号，正常的组内中心化就能解释；不能等同于 Adam 没有更新 |

40 条 Depot 优先中，32 条是初始开局，5 条是 01:47/01:51，另外 3 条人口余量
为 27/31/38；没有“人口已满之后主动纠错”的训练样本。
另有 **21 条合法回答在第一座 Depot 前安排的 Marine/SCV 数超过输入的人口余量**。
这只是潜在阻塞风险，不是已证实超时：后续死亡、已有施工、实际执行都能改变人口。
不能用“查询时余量大于零”认定计划合理。

因此本批**数量不同，却没有回报排名**；这些是模型选择，不声称全部单位实际建成。
原日志 `prompt_response.jsonl` 第 153–160 行。第 3 步则两答均完全相同，八局一起失败。

前两步不是“完全没训练信号”。例如第 1 步相同开局输入，env4 三答、env3 十一答，
最终都 20.5；`gamma=0.95` 算出的首答未中心化折扣回报分别 **18.50125 / 12.27411**。
这是按 Planner 决策次数折扣，**不是按游戏用时**。它提供了少调用方向的信号，
但不能直接解释为“学会避免人口阻塞”，也不能仅凭这个标量认定参数更新方向。

计分依据均为上述冻结 SHA：

- `planner.py:1077`：终局 Victory +20；最后回答合法 +0.5；非胜利另有终局状态分。
- `commander.py:284`：阶段奖励/攻击标记奖励；step2 额外 +0.5 与攻击标记路径一致，
  不能误写为“多生成任意合法回答就 +0.5”。
- `gigpo/core_gigpo.py:87,174,338`：按决策序列折扣，episode 与相同输入的 step 分组中心化。
- `ray_trainer.py:201,1219,1310`：另扣无效回答 0.1；折扣之后、优势计算前还有补齐/平衡。
- `dp_actor.py:438`：策略损失外还有 entropy/ref-KL；step3/4 梯度范数 0.021/0.025，
  加上 Adam 动量，不能说“advantage 为零所以模型参数必然不变”。

表中 0 按日志精度报告，不主张原始 FP32 张量逐位为零。
step1/2 分别复制补齐 3/1 条，未保存复制 ID、平衡顺序和原 advantage 张量；
这里不伪造逐答精确优势或参数梯度归因。step3/4 不需补齐；同输入、同长度、同奖励
且全合法，已足够解释日志中的零相对信号。
